## 2. 需求規格（SA）

### 2.1 角色與權責

| 角色代碼 | 角色名稱 | 供應商端關聯責任 |
|---|---|---|
| ACT-S | 供應商 | 訂單確認接單、出貨管理、送達回報、異常回報 |
| ACT-P | 平台管理者 | 發送通知信、監控供應商履約、異常處理 |
| ACT-C | 客戶端使用者 | 下單付款、接收配送狀態更新 |
| ACT-O | 機構管理者 | 查詢訂單履約進度 |
| SYS | 系統自動 | 訂單通知信發送、逾期提醒 |

### 2.2 功能需求（FR-S）

- FR-S-001：供應商密碼驗證閘門（以供應商密碼單一驗證）。
- FR-S-002：供應商訂單列表總覽（含狀態篩選、搜尋、統計摘要）。
- FR-S-003：單筆訂單詳情檢視（訂單資訊、配送資訊、商品明細）。
- FR-S-004：確認接單（含預計出貨日期）。
- FR-S-005：填寫出貨資訊（物流公司、追蹤編號、出貨日期）。
- FR-S-006：確認送達回報。
- FR-S-007：無法接單回報（含原因分類）。
- FR-S-008：配送異常回報（延遲、損壞、拒收等）。
- FR-S-009：訂單操作歷程查詢。
- FR-S-010：訂單通知信發送（系統自動觸發）。

#### UC-S-01 供應商身份驗證

- 前置：供應商收到平台寄發之訂單通知信，信中包含供應商專屬連結。
- 主流程：
  1. 供應商點擊通知信中的連結（連結帶有供應商 ID 與訂單編號參數）。
  2. 顯示密碼驗證閘門（含訂單編號或供應商名稱預覽）。
  3. 供應商輸入與平台約定的密碼。
  4. 系統驗證密碼正確 → 顯示訂單頁面。
- 例外：
  - 密碼錯誤 → 累計錯誤次數，顯示剩餘嘗試機會。
  - 超過 5 次嘗試 → 鎖定頁面，須聯絡平台客服重置。
- 後置：進入已驗證狀態，可操作訂單管理功能。

#### UC-S-02 查詢訂單列表

- 前置：已通過身份驗證。
- 主流程：
  1. 顯示該供應商所有訂單之統計摘要（待確認/待出貨/配送中/已完成）。
  2. 預設顯示全部訂單，按日期倒序排列。
  3. 可透過狀態 Tab 篩選（全部/待確認/待出貨/配送中/已完成）。
  4. 可透過搜尋框以訂單編號搜尋。
  5. 可選擇日期範圍（近 30 日/近 3 個月/近半年/全部）。
  6. 點擊「處理訂單」/「查看詳情」進入訂單內頁。
- 後置：無狀態變更。

#### UC-S-04 確認接單

- 前置：訂單狀態為 `notified`（待確認）。
- 主流程：
  1. 供應商填寫預計出貨日期（必填）。
  2. 填寫接單備註（選填）。
  3. 按下「確認接單」。
  4. 系統更新訂單狀態為 `confirmed`。
  5. 啟用「填寫出貨資訊」步驟。
  6. 寫入操作歷程。
  7. 通知平台端訂單已確認。
- 例外：未填寫預計出貨日 → 提示必填。
- 後置：狀態由 `notified` → `confirmed`。

#### UC-S-05 填寫出貨資訊

- 前置：訂單狀態為 `confirmed`（待出貨）。
- 主流程：
  1. 選擇物流公司（必填）。
  2. 填寫貨運追蹤編號（必填）。
  3. 填寫實際出貨日期（必填）。
  4. 填寫出貨備註（選填）。
  5. 按下「確認出貨」。
  6. 系統更新訂單狀態為 `shipped`。
  7. 啟用「送達確認」步驟。
  8. 寫入操作歷程。
  9. 通知平台端與客戶端已出貨（含物流追蹤資訊）。
- 後置：狀態由 `confirmed` → `shipped`。

#### UC-S-06 確認送達

- 前置：訂單狀態為 `shipped`（配送中）。
- 主流程：
  1. 供應商確認貨物已送達。
  2. 系統更新訂單狀態為 `delivered`。
  3. 寫入操作歷程。
  4. 通知平台端訂單已完成配送。
- 後置：狀態由 `shipped` → `delivered`。

#### UC-S-07 拒絕接單

- 前置：訂單狀態為 `notified`（待確認）。
- 主流程：
  1. 供應商選擇無法接單原因（商品缺貨/商品已停產/配送區域限制/其他）。
  2. 填寫詳細說明（選填）。
  3. 按下「確認拒絕」。
  4. 系統更新訂單狀態為 `rejected`。
  5. 寫入操作歷程。
  6. 通知平台端供應商拒絕，由平台另行安排。
- 後置：狀態由 `notified` → `rejected`。

#### UC-S-08 回報配送異常

- 前置：訂單狀態為 `shipped`（配送中）。
- 主流程：
  1. 供應商選擇異常類型（配送延遲/部分商品缺貨/商品損壞/地址無法送達/收件人拒收/其他）。
  2. 填寫異常說明（選填）。
  3. 按下「送出回報」。
  4. 系統建立異常記錄。
  5. 寫入操作歷程。
  6. 通知平台客服介入處理。
- 後置：訂單狀態不變，額外建立 issue 記錄。

### 2.4 業務規則（供應商端關聯）

- BR-SUP-001：通知信連結帶有供應商 ID 與訂單編號，僅供識別用途。
- BR-SUP-002：供應商密碼由平台端分配與管理，為供應商唯一驗證方式。
- BR-SUP-003：密碼驗證最多嘗試 5 次，超過即鎖定頁面。
- BR-SUP-004：收件人資訊直接顯示完整內容，供應商取得配送所需資訊。
- BR-SUP-005：確認接單後不可反悔（需聯絡平台客服處理）。
- BR-SUP-006：出貨資訊送出後不可自行修改（需聯絡平台客服）。
- BR-SUP-007：訂單狀態推進為單向流程，不可逆向操作。
- BR-SUP-008：供應商拒絕接單後，平台須於 24 小時內另行安排或通知客戶。
- BR-ORD-001：訂單金額以建立當下快照為準。
- BR-AUD-001：供應商所有操作必寫入操作歷程日誌。

### 2.5 狀態模型（供應商端訂單流程）

#### 供應商訂單狀態機

```
                              ┌──────────┐
                              │ rejected │ (無法接單)
                              └──────────┘
                                    ▲
                                    │ reject
                                    │
paid ──(通知)──► notified ──(接單)──► confirmed ──(出貨)──► shipped ──(送達)──► delivered
                 (待確認)             (待出貨)              (配送中)            (已完成)
                                                               │
                                                               ├── issue_reported (異常回報)
                                                               │   (狀態不變，建立 issue 記錄)
```

| 狀態 | 代碼 | 說明 | 允許操作 |
|---|---|---|---|
| 已付款 | `paid` | 客戶完成付款，系統準備通知供應商 | — |
| 已通知 | `notified` | 通知信已寄出，等待供應商回應 | 確認接單、拒絕接單 |
| 已確認 | `confirmed` | 供應商已接單，準備出貨 | 填寫出貨資訊 |
| 已出貨 | `shipped` | 貨物已交由物流配送 | 確認送達、回報異常 |
| 已送達 | `delivered` | 配送完成 | — |
| 已拒絕 | `rejected` | 供應商無法接單 | — |

### 2.7 非功能需求（供應商端關聯）

- NFR-S-001：通知信須於訂單付款完成後 5 分鐘內發送。
- NFR-S-002：供應商頁面須支援行動裝置（響應式設計），因供應商可能以手機閱信後直接操作。
- NFR-S-003：密碼驗證須在後端完成，前端不可明文存放密碼。
- NFR-S-004：密碼驗證須搭配 Rate Limiting，防止暴力破解攻擊。
- NFR-S-005：收件人資訊直接顯示完整內容，供供應商配送使用。
- NFR-S-006：頁面載入 P95 < 2 秒。
- NFR-S-007：供應商操作須全量記錄於 audit_log（含 IP、User-Agent）。
- NFR-S-008：HTTPS 強制啟用，密碼傳輸須加密。

## 3. 系統設計（SD）

### 3.1 設計目標

1. 讓供應商透過一頁式網站即可完成訂單確認、出貨、送達回報，無需登入系統帳號。
2. 以供應商密碼單一驗證確保安全性，同時降低供應商使用門檻。
3. 所有操作具備完整稽核追溯能力。
4. 狀態推進即時同步至平台端與客戶端。

### 3.2 架構定位

- Presentation：4.供應商端（純靜態 HTML + JS，無需建置框架）
- API Layer：`/api/v1` + 供應商密碼驗證
- Domain Services：SupplierNotification、SupplierOrder、AuditLog
- Data：SQL Server（命名規範：tbl 表名 / c 欄位 / 小駝峰）
- External：Email Service（通知信發送）

### 3.3 通知信觸發流程

```
客戶端付款完成 (paid)
    │
    ▼
OrderService.afterPaymentConfirmed()
    │
    ├─ 1. 更新 orders.status = 'paid'
    ├─ 2. 查詢 order_items 對應的 supplier_id
    ├─ 3. 依 supplier 分組
    │
    ├─ 4. 組合通知信內容（HTML 模板）
    │     ├── 訂單編號、建立時間
    │     ├── 商品摘要（品名 × 數量）
    │     ├── 列表頁連結：/supplier-orders.html?supplier={supplier_id}
    │     └── 單筆連結：/supplier-order.html?order={order_id}
    │
    ├─ 5. 呼叫 EmailService 發送通知信
    └─ 6. 更新 orders.status = 'notified'，寫入 order_status_logs
```

### 3.4 模組設計

| 模組 | 職責 | 主要資料表 |
|---|---|---|
| SupplierNotification | 通知信發送、身份驗證 | tblSuppliers |
| SupplierOrder | 訂單查詢、狀態推進、出貨資訊管理 | tblOrders、tblOrderItems、tblOrderStatusLogs、tblSupplierShipments |
| IssueReport | 配送異常回報 | tblSupplierIssues |
| AuditLog | 操作歷程記錄 | tblSupplierAuditLogs |

#### 3.5.2 cOrderStatus 狀態碼擴充對照

| INT 值 | 狀態碼 | 中文 | 來源 | 備註 |
|---|---|---|---|---|
| 0 | pending_payment | 待付款 | 系統原有 | — |
| 1 | paid | 已付款 | 系統原有 | 觸發供應商通知 |
| 2 | notified | 已通知供應商 | 🆕 供應商端 | 通知信寄出 |
| 3 | confirmed | 供應商已確認 | 🆕 供應商端 | 供應商接單 |
| 4 | shipped | 已出貨 | 🆕 供應商端 | 填寫物流資訊 |
| 5 | delivered | 已送達 | 🆕 供應商端 | 配送完成 |
| 6 | completed | 已完成 | 系統原有 | 原 processing 與 completed 合併 |
| 7 | refund_pending | 退款待審 | 系統原有 | — |
| 8 | refunded | 已退款 | 系統原有 | — |
| 9 | cancelled | 已取消 | 系統原有 | — |
| 10 | rejected | 供應商拒絕 | 🆕 供應商端 | 供應商無法接單 |

> 原系統 `processing` 狀態被細分為 `notified → confirmed → shipped → delivered` 四階段，以支援供應商履約追蹤。

| 系統原有欄位 | 供應商端對應 | 匹配狀態 | 說明 |
|---|---|---|---|
| order_id | 關聯訂單 | ✅ 匹配 | — |
| from_status | 前狀態 | ⚠️ 需改 INT | 改用 INT 對應 3.5.2 狀態碼 |
| to_status | 後狀態 | ⚠️ 需改 INT | 改用 INT 對應 3.5.2 狀態碼 |
| operator_id | 操作者 | ⚠️ 需擴充 | 原 FK→users，供應商非 users 表，見下方說明 |
| reason | 原因 | ✅ 匹配 | — |
| — | 🆕 cSupplierId | 🆕 需新增 | 若操作者為供應商，記錄 FK → tblSuppliers |
| — | 🆕 cOperatorType | 🆕 需新增 | INT：0=系統 / 1=使用者 / 2=供應商 |

> **operator_id 擴充說明**：原設計 operator_id 僅 FK→users，但供應商不在 users 表中。最小成本方案：新增 `cOperatorType`（INT）區分操作者類型，`cSupplierId`（BIGINT NULL）記錄供應商操作者，原 `operator_id` 保留給 users 操作。

### 3.8 API 規格（供應商端）

#### 共通規範

- Base URL：`/api/v1/supplier`
- 認證：Bearer Token（由密碼驗證後換發 session token）
- 格式：application/json
- 追蹤：x-request-id

#### 核心 API

| API | 方法 | 說明 | 請求/回應摘要 |
|---|---|---|---|
| /api/v1/supplier/auth | POST | 驗證供應商密碼 | `{ supplier_id, password }` → `{ session_token, supplier_name }` |
| /api/v1/supplier/orders | GET | 查詢供應商訂單列表 | `?status=&page=&limit=&date_from=&date_to=&keyword=` → `{ orders[], total, page }` |
| /api/v1/supplier/orders/{id} | GET | 取得單筆訂單詳情 | → `{ order, items[], shipment, history[] }` |
| /api/v1/supplier/orders/{id}/confirm | POST | 確認接單 | `{ estimated_ship_date, note? }` → `{ success, order_status }` |
| /api/v1/supplier/orders/{id}/ship | POST | 確認出貨 | `{ carrier, tracking_number, ship_date, note? }` → `{ success }` |
| /api/v1/supplier/orders/{id}/deliver | POST | 確認送達 | `{}` → `{ success }` |
| /api/v1/supplier/orders/{id}/reject | POST | 拒絕接單 | `{ reason, detail? }` → `{ success }` |
| /api/v1/supplier/orders/{id}/issues | POST | 回報配送異常 | `{ issue_type, description? }` → `{ success, issue_id }` |

#### 驗證流程 API 詳細說明

**POST /api/v1/supplier/auth**

Request：
```json
{
    "supplier_id": "URL 中的供應商 ID 參數",
    "password": "供應商輸入的密碼"
}
```

Response（成功）：
```json
{
    "success": true,
    "session_token": "server-issued-session-jwt",
    "supplier_name": "健康生活有限公司",
    "expires_in": 3600
}
```

Response（失敗）：
```json
{
    "success": false,
    "error": "INVALID_PASSWORD",
    "remaining_attempts": 3
}
```

Response（鎖定）：
```json
{
    "success": false,
    "error": "ACCOUNT_LOCKED",
    "message": "嘗試次數過多，請聯絡平台客服。"
}
```

### 3.11 安全設計

| 項目 | 措施 |
|---|---|
| 密碼儲存 | bcrypt（cost factor ≥ 12） |
| 驗證次數限制 | 最多 5 次，超過鎖定該供應商帳號 |
| 收件人資訊 | 直接顯示完整內容，不做遮罩處理 |
| 傳輸安全 | HTTPS 強制，HSTS header |
| Session | 驗證通過後發放 JWT，有效期 1 小時，不可續約 |
| CORS | 僅允許平台網域 |
| Rate Limiting | 每 IP 每分鐘最多 10 次驗證嘗試 |
| 連結安全 | 連結僅含供應商 ID 與訂單編號作為識別，不含機密資訊 |

### 3.12 非功能設計（實作向）

- 通知信採 Queue 機制發送，避免付款流程阻塞。
- 訂單列表 API 需分頁（預設每頁 20 筆）與索引優化。
- 供應商操作需全量寫入 tblSupplierAuditLogs。
- EmailService 異常採降級策略（寫入重試佇列，最多重試 3 次）。
- 前端為純靜態頁面，可部署於 CDN 或 Static Hosting。
